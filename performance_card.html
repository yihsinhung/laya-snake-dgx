指標說明Metric glossary

下表每個項目代表的意義,以及怎麼讀。What each metric means and how to read it.

421M / 322M
兩種 Laya 模型:421M = convaiinnovations/laya(ModernBERT-large encoder,英文單語);322M = convaiinnovations/laya-multilingual(mmBERT-base encoder,100+ 語言)。兩者都輸出「typed decision」,但參數量與 encoder 不同。 Two Laya models: 421M = convaiinnovations/laya (ModernBERT-large encoder, English); 322M = convaiinnovations/laya-multilingual (mmBERT-base encoder, 100+ languages). Both output typed decisions but differ in size and encoder.
One short question · P50
對一個簡短問題做一次完整推論的延遲(ms)。P50 = 中位數(一半更快、一半更慢),最具代表性的「典型延遲」。 Latency (ms) for one full inference on a single short question. P50 = median (half faster, half slower), the representative "typical latency".
One short question · P95
同一次推論延遲的第 95 百分位。代表「最慢的 5% 也不超過這個值」,用來評估延遲的上限與穩定性。 The 95th percentile of the same latency. Represents the slowest 5% ceiling, evaluating the upper bound and stability of latency.
50-question throughput
把 50 個問題一次送進模型(單次大型 batch)的每秒處理問卷數(q/s)。反映批量吞吐能力,即 GPU 攤平固定開銷後的真實運算上限。 How many questions the model can process per second when 50 are batched at once (q/s). Reflects batch throughput, the real compute ceiling after fixed overhead is amortized.
Peak GPU allocation
處理一個單問時的峰值記憶體佔用(GB10 用 MB,M3 Max 官方表用 MiB;1 MiB ≈ 1.048 MB)。含模型權重 + forward 暫存,評估記憶體需求。 Peak memory while processing one question (GB10 in MB, M3 Max official in MiB; 1 MiB ≈ 1.048 MB). Includes weights + forward buffers, assessing memory footprint.
Snake · steps/s
在 Laya Snake「headless 全速」模式下,每秒完成的遊戲決策步數。這是遊戲場景的實際吞吐,含推理+規劃+作畫準備。 Game decisions per second in Laya Snake headless full-speed. Real in-game throughput, including inference + planning + render prep.
Snake · mean inference
Snake 中每次決策的平均模型推論時間(ms)。是純 agent.predict 均值,不含遊戲/UI 與規劃開銷。 The average model inference time per decision in Snake (ms). Pure agent.predict mean, excluding game/UI/planning overhead.

為什麼這些數字不一樣Why the numbers differ

同一顆模型在不同硬體、不同模型大小下,單發延遲與吞吐的關係並不一致。The same model behaves differently across hardware and model sizes: latency and throughput don't scale together.

01

單問延遲,GB10 為什麼追平 M3 MaxWhy single-question latency matches

單一短問題是極小的 batch,Blackwell 龐大算力只跑一兩顆小 kernel 就結束。此時瓶頸不在 GPU,而在每呼叫的固定開銷:PyTorch eager dispatch、autocast 初始化、tokenization、Python 呼叫機制。這層在 batch=1 時吃掉大部分優勢,把 GB10 拉到跟 MLX(M3 Max)差不多。 A single short question is a tiny batch; Blackwell's massive compute finishes in one or two small kernels. The bottleneck is per-call fixed overhead: PyTorch eager dispatch, autocast init, tokenization, Python call machinery. At batch=1 this eats most of the advantage, pulling GB10 down to near MLX (M3 Max).

02

批量吞吐,GB10 為什麼翻倍Why batch throughput doubles

把 50 個問題合成一次大型 forward 後,固定開銷被攤平,真正的 GPU 運算量變成主導。Blackwell 的原始吞吐優勢完全釋放:421M 從 147 拉到 641 q/s,322M 從 395 拉到 1300 q/s。延遲取決於運行時開銷,吞吐取決於矽晶運算力。 Batching 50 questions into one large forward amortizes fixed overhead, so true GPU compute dominates. Blackwell's raw throughput advantage fully shows: 421M jumps 147→641 q/s, 322M 395→1300 q/s. Latency depends on runtime overhead, throughput on silicon.

03

322M 為什麼比 421M 快Why 322M is faster than 421M

ModernBERT-large(421M)是更大的 encoder,每 token FLOPs 與 activation 都高於 mmBERT-base(322M)。小 batch 下差異直接放大:延遲約 2 倍(15.8 vs 7.2 ms),吞吐約 2 倍(641 vs 1300)。模型越大越慢是常態,322M 是速度與品質的較佳平衡。 ModernBERT-large (421M) is a larger encoder with more per-token FLOPs/activations than mmBERT-base (322M). At small batch the gap compounds: ~2x latency (15.8 vs 7.2 ms), ~2x throughput (641 vs 1300). Bigger is slower; here 322M is the better speed/quality balance.

04

GB10 峰值記憶體為什麼較高Why GB10 peak memory is higher

權重都約 0.8GB(421M fp16),但 GB10 顯示 2499 / 1638 MB,高於 M3 Max 的 943.6 / 687.6 MiB。差距來自 forward 後仍被保留的 PyTorch 運行時足跡:autocast context、activation buffer、CUDA workspace。這是每 session 的運行時佔用,不是模型大小。 Weights are ~0.8GB (421M fp16), but GB10 shows 2499 / 1638 MB vs M3 Max's 943.6 / 687.6 MiB. The gap is the retained PyTorch runtime footprint after forward: autocast context, activation buffers, CUDA workspace. That's per-session runtime overhead, not model size.
